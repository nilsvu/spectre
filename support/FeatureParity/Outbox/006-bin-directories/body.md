# Survey: bin directories — freeze what a scheduled run depends on

Surveyed revisions: SpEC sxs-collaboration/spec@653caf4736, SpECTRE sxs-collaboration/spectre@4d43624d64. All `file:line` below refer to those revisions.

## Verdict

**Partial parity.** SpECTRE already snapshots the *executable* and the *submit-script templates* into the segments directory, so recompiling does not change which binary a queued or restarting segment runs. It does **not** snapshot the Python/CLI half of the machinery, and that half is on the critical path of every segment boundary and every pipeline handoff: the generated `Submit.sh` calls `${SPECTRE_CLI} resubmit` and `${SPECTRE_CLI} run-next` with `SPECTRE_CLI` pointing straight into the build directory (`support/SubmitScripts/SubmitTemplateBase.sh:21,92,102` with `support/Python/Schedule.py:695`). Five machine templates additionally `source` an environment script out of the live *source* tree. So today: rebuild the C++ and a running simulation is safe; edit a Python file, switch branches, or delete the build directory, and the next segment or the next pipeline step changes behaviour or fails — after the job has already burned its wallclock.

Three narrower defects fall out of the same root cause and are listed under "What breaks today".

## What SpEC does

**One routine builds the whole thing:** `SpEC::MakeBinDir` at `Support/Perl/SpEC.pm:35-132`. It creates a run-local directory and copies (or, with `-L`, symlinks) a fixed set of files into it.

**Contents of a SpEC bin directory** (`Support/Perl/SpEC.pm:47-107`): every Perl module of the code base (`Support/Perl/*.pm`), the machine environment file (`MakefileRules/this_machine*.env`), roughly fifty explicitly named support tools (`DoMultipleRuns`, `MakeNextSegment`, `MakeSubmit.py`, `MakeBinDirectory`, `EvolutionWrapper`, `Restart.py`, `OmegaDotEccRemoval.py`, `ManageRuns.py`, …), optionally the hydro tools, and the main executable itself.

**Plus provenance, written at creation time** (`Support/Perl/SpEC.pm:129-131`): `bin/env.log` from `printenv` and `bin/module.log` from `module list`. These are recorded, not replayed — SpEC does not freeze the module environment itself.

**A symlink names the executable**: `bin/../SpEC -> bin/<ExecName>` (`Support/Perl/SpEC.pm:122-127`), so every script and input file refers to `./SpEC` and never to a build path.

**The snapshot is taken at run setup, not at submit time.** `PrepareEv` creates it in the evolution directory from `$CODE_HOME/Support/bin` plus the executable (`Support/Perl/PrepareEv.pl:93-95`); `PrepareID` does the same for initial data (`Support/Perl/PrepareID.pl:136-138`). Both skip the work if `bin` already exists.

**Per-Lev directories link, they do not re-copy.** The generated `StartJob.sh` runs `bin/DoMultipleRuns -L …` (`Support/Perl/PrepareEv.pl:138`), and `DoMultipleRuns` defaults its bin source to the directory it was itself invoked from (`Support/Perl/DoMultipleRuns.pl:32,196`) and its executable to `$CWD/SpEC` (`Support/Perl/DoMultipleRuns.pl:168`). So the one physical copy in the evolution directory is what every Lev's `bin/` points at (`Support/Perl/DoMultipleRuns.pl:275-283`).

**Segment N+1 inherits segment N's bin by relative symlink.** `BatchJobTermination::LinkSpec` (`Support/Perl/BatchJobTermination.pm:2683-2695`) links both `SpEC` and `bin` into the new segment via `Utils::LinkToOriginal` (`Support/Perl/Utils.pm:225-231`), which resolves the symlink chain to the original and then writes a *relative* link. Every automatic continuation path goes through it (`Support/Perl/BatchJobTermination.pm:522,1052,1165,1253,1314,1415,1510,2109,2726`).

**The batch job runs with the frozen bin first on `PATH`.** The `Submit.sh` header generated by `MakeSubmit.py` is `. bin/this_machine.env` followed by `export PATH=$(pwd -P)/bin:$PATH` (`Support/Python/MakeSubmit.py:163-168`), and the default job script is just `EvolutionWrapper …` (`Support/Python/MakeSubmit.py:104-105`) — resolved from that bin. Perl scripts self-locate the same way: each does `use lib dirname(abs_path(__FILE__))` and therefore loads the `.pm` files sitting next to it in the bin directory (`Support/Perl/SpEC.pm:18-25`, `Support/Perl/DoMultipleRuns.pl:25-32`).

**Scripts re-exec themselves out of the target bin.** `MakeNextSegment` and `MakeBinDirectory` both compare their own realpath against the one in the source bin and re-invoke from there if they differ (`Support/Perl/MakeNextSegment.pl:110-118`, `Support/Perl/MakeBinDirectory.pl:70-79`). This is what keeps a continuation on the frozen scripts even when the user typed the repo's copy.

**A third layer at job start**: `EvolutionWrapper` copies `WORK/SpEC` into the run's scratch directory (`$WORK/Run` on most machines — `Support/Perl/Machines.pm:1674-1677`) and executes `./SpEC` there (`Support/Perl/EvolutionWrapper.pl:329-338,207-229`). The binary a job actually executes is therefore a private copy made after the job started.

**Deliberate update is an explicit, first-class operation.** `MakeNextSegment -E <exec-in-a-repo>` (or `-b`/`-e`) rebuilds the bin from the new source instead of inheriting, deleting the auto-generated one first (`Support/Perl/MakeNextSegment.pl:82-99,173-219`); with none of those flags it inherits from the previous segment (`Support/Perl/MakeNextSegment.pl:96-99`). `MakeBinDirectory` does the same by hand and is documented as "typically … only when debugging runs" (`Support/Perl/MakeBinDirectory.pl:15-40`). The environment is re-established from the bin, not from the login shell: `SpEC::LoadEnvFromBin` sources `bin/this_machine.env` and prepends the bin to `PATH` (`Support/Perl/SpEC.pm:136-155`, called at `Support/Perl/MakeNextSegment.pl:126`).

There is a black-box test of the contract at `Support/Tests/TestMakeBinDirectory/run_test`.

## What SpECTRE does today

**Executable — snapshotted, for segment runs only.** `support/Python/Schedule.py:686-689` copies the resolved executable into the segments directory when `--segments-dir` / `-O` is used (default `copy_executable=None` behaves as "copy" there). `_copy_to_dir` returns early when the source already lives in the destination (`support/Python/Schedule.py:90-91`), so later segments reuse the one copy rather than re-copying from the build directory — verified in `tests/support/Python/Test_Schedule.py:228-229`.

**Executable — not snapshotted for `--run-dir` / `-o` runs** unless `--copy-executable` is passed explicitly (`support/Python/Schedule.py:594-596`, option docs at `support/Python/Schedule.py:882-900`). A plain `spectre schedule -o …` bakes the build-directory path into `Submit.sh`.

**Submit-script templates — snapshotted.** The machine template and the `SubmitTemplateBase.sh` it inherits from are both copied to the segments directory (`support/Python/Schedule.py:103-119,701-708`).

**Input file and scheduler context — snapshotted per segment.** The rendered input file is written into the segment, and `SchedulerContext.yaml` records the parameters used (`support/Python/Schedule.py:547-566,723-726`). `Resubmit.py:52-73` reads that context back and re-enters `schedule()` with it.

**CLI and Python package — not snapshotted.** `spectre_cli` is computed as `Path(__file__).parent.parent.parent.parent / "spectre"` (`support/Python/Schedule.py:691-697`), i.e. `<build_dir>/bin/spectre`. That path is written into the submit script (`support/SubmitScripts/SubmitTemplateBase.sh:21`) and invoked after the executable exits, for both resubmission and the pipeline handoff (`support/SubmitScripts/SubmitTemplateBase.sh:92,102`). `<build_dir>/bin/spectre` is a generated wrapper that sets `PYTHONPATH` into `<build_dir>/bin/python` and runs `python -m spectre` (`cmake/SpectrePythonExecutable.sh:6-7`, `cmake/SpectreSetupPythonPackage.cmake:66-72`, `CMakeLists.txt:83-89`).

**Machine configuration — not snapshotted.** `this_machine()` reads `Machine.yaml` from the build-directory package (`support/Python/Machines.py:105`, configured there by `support/Python/CMakeLists.txt:24-40`).

**Pipeline templates and next-step executables — not snapshotted.** `Next` entrypoints are Python module paths imported at handoff time (`support/Pipelines/Bbh/Inspiral.yaml:8-18`, `support/Python/RunNext.py:64-80`), and each step reads its input-file template from its own package directory (`support/Pipelines/Bbh/Inspiral.py:22`, `support/Pipelines/Bbh/Ringdown.py:28`) and resolves its executable freshly from `PATH` plus the build directory (`support/Python/Schedule.py:39-58`).

**Environment — not snapshotted, and on five machines sourced from the live source tree.** `support/SubmitScripts/Urania.sh:28` and `support/SubmitScripts/Deucalion.sh:32` bake `@CMAKE_SOURCE_DIR@/support/Environments/<machine>.sh` into the submit script at CMake-configure time; `support/SubmitScripts/Anvil.sh:38`, `support/SubmitScripts/Expanse.sh:55` and `support/SubmitScripts/Viper.sh:26` go through `${SPECTRE_HOME}` — which `Viper.sh` never sets, so it is inherited from the submitting shell.

**Python files may be symlinks into the source tree.** With `PY_DEV_MODE=ON` the build directory's package contains symlinks rather than copies (`cmake/SpectreSetupPythonPackage.cmake:7-18`, `docs/Installation/BuildSystem.md:178-183`). Default is `OFF`, so a rebuild is normally required to propagate a Python edit — but only `cmake` needs to re-run, not a compile.

**Provenance is already stronger than SpEC's.** Formaline is on by default (`cmake/SetupFormaline.cmake:84-86`), embeds a gzipped source archive plus link-time `printenv` and build info into every executable (`tools/Formaline.sh:8-33`), and every H5 file written carries the archive at `/src` (`src/IO/H5/File.cpp:155`) with the environment in its header (`src/Parallel/Main.hpp:384-398`). This records what ran; it does nothing to keep the *next* segment on the same code.

**Measured, not inferred:** `BUILD_SHARED_LIBS` defaults to `OFF` (`docs/Installation/BuildSystem.md:88-90`), and `ldd` on a release-build BBH executable in this environment lists 49 shared objects, none of them inside the build directory. Copying the executable is therefore a valid snapshot for a default build. With `BUILD_SHARED_LIBS=ON` it silently is not.

**Negative results.** Searched `support/`, `src/`, `cmake/` and `tools/` for any run-local `bin/` directory, PATH manipulation in submit scripts, CLI copying, or environment freezing: nothing exists. `PATH` is never modified by `SubmitTemplateBase.sh`. There is no equivalent of SpEC's `LoadEnvFromBin`, no equivalent of `MakeBinDirectory`, and no manifest or hash of what a run depends on.

## What breaks today

- **Deleting or moving the build directory kills every queued and future segment**, because `SPECTRE_CLI` and (for `-o` runs) `SPECTRE_EXECUTABLE` are absolute build-directory paths. Failure happens after the run finishes, so the wallclock is spent first.
- **Editing a Python file and re-running `cmake` changes the behaviour of running simulations** at their next segment boundary or pipeline handoff, since `resubmit` and `run-next` execute whatever is in the build directory then.
- **Switching branches in the source tree changes the loaded module environment** on Urania and Deucalion, where the submit script sources `@CMAKE_SOURCE_DIR@/support/Environments/<machine>.sh` at job start.
- **A mid-pipeline recompile changes the executable used by later pipeline steps**, because each step resolves its executable afresh and copies it into its *own* step directory (`support/Python/DirectoryStructure.py:131-183` for the step layout, `support/Python/Schedule.py:686-689` for the copy). Inspiral and ringdown of one simulation can end up built from different sources without anything recording it.
- **Inference, not observed:** because `Resubmit.py` feeds a stored `SchedulerContext.yaml` into whatever `schedule()` signature is current, a schema change to that context between two segments of a long run would silently change or break resubmission. An implementer should confirm this before relying on it as motivation.

## Proposed design

**Shape.** One run-local `bin/` per *simulation*, created once, containing everything a submitted job needs after submission; every generated `Submit.sh` resolves the executable, the CLI, and the environment from it and from nothing else. This is SpEC's model minus the per-segment symlink farms that #5951 calls out as a mistake.

**Where it lands.** `<pipeline_dir>/bin/` when a pipeline directory exists (`spectre bbh …`), so initial data, inspiral, ringdown and every segment share one snapshot; `<segments_dir>/bin/` for a bare `spectre schedule -O`; `<run_dir>/bin/` for `-o` with the snapshot enabled. The existing `<segments_dir>/<Executable>` copy moves inside `bin/`.

**What lands in it** (recommendation; see open point 1):

- every executable the pipeline will run, resolved once at snapshot time — not just the first step's;
- `bin/spectre`, a wrapper equivalent to `cmake/SpectrePythonExecutable.sh` but with `PYTHONPATH` pointing at `bin/python`, plus `bin/python/spectre/` — a copy of the build directory's package including its compiled `*_Pybindings*.so` and the configured `Machine.yaml`;
- `bin/env.sh` — a copy of the machine environment script the submit template currently sources from the source tree;
- the submit-script template and its base (already copied today, just relocated);
- `bin/env.log` (`printenv`) and `bin/module.log` (`module list`) — direct parity with `Support/Perl/SpEC.pm:129-131`;
- `bin/Manifest.yaml` — build directory, source revision, CMake options, snapshot timestamp, and a SHA256 per copied file. This is what #7442's sanity checks and any post-hoc audit read.

**When it is taken.** At the first `schedule()` call that would create it, i.e. at pipeline start or first `-O` submission. Never re-taken implicitly — a later `schedule()` that finds `bin/` reuses it, which is the behaviour `_copy_to_dir`'s early return already gives for the executable (`support/Python/Schedule.py:90-91`). Explicit update only (open point 4).

**How segments and restarts resolve it.** Pipeline-side, in three places:

- `support/Python/Schedule.py`: set `spectre_cli` to `<bin_dir>/spectre` when a bin directory exists, replacing the build-directory computation at line 695; put `<bin_dir>` at the front of the search path in `_resolve_executable` (lines 39-58), mirroring SpEC's `PATH` prepend; record `bin_dir` in `SchedulerContext.yaml`.
- `support/SubmitScripts/SubmitTemplateBase.sh`: add `export SPECTRE_BIN_DIR={{ bin_dir }}`, `export PATH=${SPECTRE_BIN_DIR}:${PATH}`, and `source ${SPECTRE_BIN_DIR}/env.sh` in the `list_modules` block; the `resubmit` and `run-next` calls then use `${SPECTRE_BIN_DIR}/spectre` by construction. The five machine templates that source the source tree drop that line and inherit the base block.
- `support/Python/Resubmit.py` needs no change beyond passing `bin_dir` through, since it already round-trips the whole context (lines 52-73).

Pipeline handoffs come along for free: because the job invokes the snapshot CLI, `run_next` imports the snapshot's `spectre.Pipelines.*`, so `Ringdown.py`, `Ringdown.yaml` and the next executable all come from the snapshot. `bin_dir` is propagated through the `Next` metadata exactly as `copy_executable` is today (`support/Pipelines/Bbh/Inspiral.yaml:16`).

**CLI / YAML knobs.**

- `--bin-dir PATH` on the scheduler options, defaulting as above; `--snapshot / --no-snapshot` as the new spelling of `--copy-executable / --no-copy-executable`, with the old flag kept as a deprecated alias so existing scripts and `Next` blocks keep working;
- `spectre update-bin BIN_DIR [-E EXEC]…` — a deliberate re-snapshot, the analogue of `MakeBinDirectory` / `MakeNextSegment -E`;
- `bin_dir` added to the context file and to the `Next` propagation list.

**Executable-side work: one guard, no new machinery.** Nothing in `src/` changes. The snapshot step should check the copied executables' `NEEDED` entries and fail if any resolves inside the build directory, turning today's silent `BUILD_SHARED_LIBS=ON` trap into an error at snapshot time. Formaline already covers provenance (`src/IO/H5/File.cpp:155`), so the bin directory does not need a source archive of its own.

**Testing / acceptance.** Extend `tests/support/Python/Test_Schedule.py` with: (a) the snapshot's contents for a segments run and for a pipeline directory — executable, `spectre` wrapper, `python/spectre` package, `env.sh`, `Manifest.yaml`; (b) a scan of the rendered `Submit.sh` and `SchedulerContext.yaml` asserting that no path under the build directory or the source directory appears — this is precisely the property this issue asks for and is cheap to assert; (c) a second `schedule()` into the same directory reuses the snapshot and copies nothing; (d) `resubmit` picks `bin_dir` out of an existing context file. Add an integration check that schedules with `--no-submit`, renames the build directory, and then runs `<bin_dir>/spectre resubmit` successfully. Acceptance for the campaign: a two-segment BBH inspiral where the source tree is switched to another branch and rebuilt between segment 0 and segment 1 — segment 1 must run the snapshot executable and CLI, confirmed by identical `/src` archives in both segments' H5 output and by the `Manifest.yaml` hashes.

## Open points to settle

- [ ] **1. Snapshot scope** — (a) executable(s) only; (b) executables + `spectre` CLI + Python package + machine env script; (c) (b) plus the full environment (shared libraries, modules, or a container image). **Recommend (b).** SpEC snapshots exactly (b): the executable plus all `Support/Perl/*.pm` and ~50 support tools plus `this_machine.env` (`Support/Perl/SpEC.pm:47-107`), while recording the module environment without freezing it (`Support/Perl/SpEC.pm:129-131`). (a) leaves the `${SPECTRE_CLI}` dependency, which is where SpECTRE actually breaks. (c) is what #5951's discussion argues toward for third-party libraries; recommend splitting it into its own issue and shipping the `NEEDED`-check guard here instead.
- [ ] **2. Where the bin directory lives, and what happens to today's copy** — (a) one per pipeline directory, falling back to the segments directory; (b) one per segments directory (i.e. per pipeline step); (c) one per segment, SpEC-style. **Recommend (a).** @nilsdeppe in #5951: "we want 1 bin directory for all Ecc iterations, levs, segments … in SpEC the execs are stored in several locations, and so sometimes not all are updated correctly". This implies today's `<segments_dir>/<Executable>` copy moves into `<bin_dir>/`; old runs keep working because `Resubmit.py` restores the absolute `executable` path from their context file. Confirm that relocation is acceptable, or keep the old path as a symlink for one release.
- [ ] **3. How the Python/CLI snapshot is built** — (a) copy the build directory's `bin/python/` tree and write a wrapper with a rewritten `PYTHONPATH`; (b) `python -m venv --system-site-packages` plus `pip install <build>/bin/python/`, as sketched in #5951; (c) wait for a pip-published package (#7448) and install a pinned version. **Recommend (a) now.** It needs no network, no pip at submit time, and no interpreter beyond the one already used; (b) additionally snapshots third-party Python dependencies, which is a real advantage — settle whether that is worth the submit-time cost and the venv failure modes. (c) should not block this issue.
- [ ] **4. Deliberate update path** — (a) a standalone `spectre update-bin` command; (b) an `--update-bin` flag on `schedule`/`resubmit`; (c) both. **Recommend (c).** SpEC has both and uses them for different situations: `MakeNextSegment -E` when continuing a run onto new code, `MakeBinDirectory` for hand-built and debug directories (`Support/Perl/MakeNextSegment.pl:82-99`, `Support/Perl/MakeBinDirectory.pl:15-40`). Also settle whether an update rewrites the snapshot in place or writes `bin.0001/` beside it — in-place loses the ability to say which segment ran which binary unless `Manifest.yaml` is append-only.
- [ ] **5. Machine environment** — (a) copy the environment script into `bin/env.sh` and source it from there; (b) keep sourcing the source tree but record its hash in the manifest; (c) capture the resolved module list and replay `module load` from it. **Recommend (a)**, which is SpEC's `this_machine.env` model (`Support/Perl/SpEC.pm:136-155`) and removes the `@CMAKE_SOURCE_DIR@` and `${SPECTRE_HOME}` dependencies in `Urania.sh`, `Deucalion.sh`, `Anvil.sh`, `Expanse.sh` and `Viper.sh` in one step. Whether module *versions* are additionally pinned belongs with #7443/#7444.
- [ ] **6. Self-containment enforcement** — (a) hard error at snapshot time if a copied executable links a shared object inside the build directory; (b) warn only; (c) no check. **Recommend (a).** `BUILD_SHARED_LIBS` defaults to `OFF` (`docs/Installation/BuildSystem.md:88-90`) and a measured release build links nothing from the build tree, so (a) costs nothing in the normal case and converts a silent, months-later failure into an immediate one. Confirm no supported workflow needs `BUILD_SHARED_LIBS=ON` for production runs.

A follow-up comment settling these points makes this issue ready for implementation (→ Ready).
